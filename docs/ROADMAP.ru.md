# План работ

Что исправил hotfix-раунд, проверенный в лаборатории (ветка `fix/lab-verified-routing`),
описано в [LAB.ru.md](LAB.ru.md). Здесь перечислено то, что в него не вошло: почему каждый
пункт важен и что значит «готово». У пунктов с пометкой **FAIL в лаборатории** есть
проверка, которая сегодня намеренно не проходит.

## Безопасность

| # | Пункт | Почему это важно | Готово, когда |
|---|---|---|---|
| 1 | **Режим Tor «Paranoid» не маршрутизирует трафик** (T1, FAIL в лаборатории) | Режим только запускает сервис Tor. Везде он помечен как экспериментальный (T2), но самой функции нет. | `nat PREROUTING -i wlan0`: tcp → TransPort 9040, udp/53 → DNSPort 5353, остальной UDP отбрасывается; INPUT открыт для обоих портов на `wlan0`; работает вместе с цепочкой `V2RAY` в том же хуке; закрывается, если Tor не установил соединение. Лаборатория: трафик клиента доходит до TransPort, а с приватной сетью Tor (chutney) сайт видит выходной узел Tor. |
| 2 | **HTTPS для панели** | Панель работает по обычному HTTP, поэтому пароль и cookie сессии идут через хотспот без шифрования, и их может прочитать любой клиент, знающий пароль Wi-Fi. Флаг `Secure` для cookie включится сам, как только запросы пойдут через TLS. | nginx отдаёт панель на 443 с локально созданным сертификатом; 8080 перенаправляет. |
| 3 | **SSH открыт на `eth0`** | `killswitch.sh` принимает tcp/22 на проводном интерфейсе со стороны WAN. За домашним роутером это нормально, в недоверенной сети — нет. | По умолчанию SSH принимается только с хотспота, для проводной стороны есть документированный переключатель. |
| 4 | **CSP всё ещё разрешает `'unsafe-inline'`** | В `index.html` используются inline-обработчики `onclick`, поэтому политика не может запретить inline-скрипты. Просмотр логов и список WAN больше не используют `innerHTML`, но автоматической проверки на XSS нет. | Обработчики перенесены в `app.js`, из CSP убран `'unsafe-inline'`, проверка в лаборатории через headless-браузер вставляет разметку в строку лога. |
| 5 | **Xray ставится через `curl … \| bash` из ветки** | От root выполняется то, что лежит в этой ветке в момент установки. v2rayA уже закреплён по версии и SHA-256, Xray — нет. | Релиз Xray закреплён, контрольная сумма проверяется до запуска. |
| 6 | **Ограничение частоты API привязано к сессии** | `check_rate_limit()` считает в `$_SESSION` — та же слабость, что была у блокировки логина. Влияние небольшое: работает только после входа. | Счётчики перенесены в серверное хранилище, которое используется для блокировки логина. |
| 7 | **Закреплённые адреса VPN обновляются только при запуске `killswitch.sh`** | Если провайдер перенесёт сервер, пока VPN не работает, VPN не сможет переподключиться до повторного запуска скрипта (см. docs/08). | Таймер заново резолвит hostname из `remote`, пока VPN работает, и обновляет правила. |
| 8 | **Для первого поиска адреса нужен настоящий резолвер в `/etc/resolv.conf`** | С заглушкой systemd-resolved (`127.0.0.53`) одноразовый запрос в `killswitch.sh` не сработает, потому что его отправляет другой процесс. | Скрипт распознаёт заглушку и использует вышестоящие серверы resolved либо ясно говорит, что делать. |

## Firewall

- **В docs/08 описано три firewall.** Устанавливается и тестируется только
  `scripts/killswitch.sh`. Конфиг nftables и пример `iptables-killswitch.sh` в том же
  документе расходятся с ним и между собой. Их нужно убрать или генерировать из одного источника.
- **Переход на nftables.** Одна атомарная загрузка `nft -f` вместо последовательности
  команд `iptables` (сейчас есть короткий момент между «очисткой» и «последним правилом»),
  именованный набор для адресов VPN, счётчики по правилам. Оба набора правил прогонять
  через лабораторию, пока все проверки не дадут одинаковый результат, затем убрать iptables.

## Функции, которые не проверены или не доделаны

- **4G failover.** `wan-switch.sh failover` и `auto` определяют, жив ли WAN, пингом
  `8.8.8.8` через него, а kill switch этот пинг отбрасывает, так что при включённом kill
  switch проверка всегда неудачна. В лаборатории есть только dummy-интерфейсы (K3a, K3b).
  Нужен другой признак живости (состояние линка или сам VPN-handshake) и настоящий модем.
- **Слой V2Ray от начала до конца.** v2rayA ставится из закреплённого релиза (I4), но
  проверки прозрачного прокси (X1–X5) идут на подставном Xray с outbound `freedom`.
  Настоящий VLESS-сервер и конфиг под управлением v2rayA не покрыты.
- **Wi-Fi хотспот.** `hostapd` не может работать в Docker; лаборатория заменяет радио
  Docker-сетью. WPA2, изоляция клиентов и производительность требуют железа.
- **Скрипты, которые упоминаются в документации, но отсутствуют в репозитории**
  (документация предлагает создать их вручную): `wan-failover.sh`, `connect-4g.sh`,
  `vpn-route-4g.sh` (docs/07), `route-through-tor.sh`, `switch-mode.sh` (docs/05),
  `iptables-killswitch.sh`, `firewall-stats.sh` (docs/08), `start-wifi.sh` (docs/06),
  `check-packages.sh` (docs/02), `collect-diagnostics.sh` (docs/11). Каждый нужно либо
  добавить в `scripts/` и протестировать, либо убрать из документации.
- **`openvpn-systemd-resolved` ставится, но не используется.** Скрипты up/down из docs/03
  пишут в `/etc/resolv.conf` напрямую. Пакет тянет за собой systemd-resolved, из-за
  которого возник конфликт портов с dnsmasq (D1 в лаборатории) и усложняется первый поиск
  адреса (пункт 8 выше). Нужно либо использовать его правильно, либо перестать ставить.
- **docs/11 всё ещё советует `rc.local`** для kill switch. Установщик теперь включает
  `shadowpi-killswitch.service`; документ должен говорить об этом.
- **Реальное железо.** Ничего из этого не запускалось на Raspberry Pi. Лаборатория
  покрывает логику, но не радио, модем, SD-карту и питание.

## Инструменты

- **CI.** Запускать `lab/lab-test.sh` в GitHub Actions (раннер arm64; контейнеру роутера
  нужны `privileged` и systemd), выгружать `lab/out/` как артефакт и ронять задачу на любом
  FAIL, которого нет в коротком списке известных (сейчас: T1).
- **Код выхода.** `lab-test.sh` всегда завершается с 0; при неожиданном FAIL он должен
  завершаться с ненулевым кодом.
- **Статические проверки в CI:** `shellcheck` для `scripts/` и `lab/`, `php -l` для `web-ui/`.
- **Язык документации.** Пошаговые гайды 00–11 существуют только на русском; README, LAB и
  ROADMAP — на трёх языках.
